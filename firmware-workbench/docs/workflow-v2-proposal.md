# 工作台工作流 v2 提案:从"流程表演"到"对齐—推进—开发"真实闭环

> 状态:提案,待评审(未批准不开发)
> 针对的问题:当前实现是一条**永不失败、永不返工、永不变更**的流水线;而真实固件研发活在**变更、失败、返工、反复对齐**里。AI(DSH)与工作台是"外挂"关系,没有流程职责。

---

## 1. 诊断:三个根本缺陷

| # | 缺陷 | 现状证据 | 真实研发的样子 |
|---|------|---------|--------------|
| D1 | **需求是一根文本,不是对话资产** | 导入 = 填 title+text,一步"完成";openQuestions 只是 Define 里一个没人处理的数组 | 大需求 → 澄清问题清单(逐题回答、可追问)→ 原子需求条目 → 评审打回/修订 v2 → 批准基线;之后还会变更 |
| D2 | **执行没有意外** | 测试失败只是任务变红;没有归因、没有缺陷、没有返工、没有重规划 | 失败 → 归因(产品/测试/环境?)→ 建缺陷 → 缺陷阻塞门禁 → 修复 → 回归 → 解锁;需求/契约变更 → 下游全部标记待重评估 |
| D3 | **AI 是外挂,不是角色** | printer_* 工具"AI 可以调",但没有任何流程节点需要 AI;DSH 会话与工作台互不相干 | 澄清问题由 AI 起草、Define 由 AI 起草人修订、失败归因 AI 建议、变更影响 AI 列举——人只做判断和签署 |

总方案 v1.0 其实都写了(12.2 追踪链与变更标记、8.11 动态重规划、11.4 失败归因、5.2 决策记录),**v1 实现只做了 happy path**。

## 2. 外部参照(调研结论)

- **GitHub Spec Kit**(spec-driven development):`/specify → /clarify → /plan → /tasks → /implement`。关键启发:**`/clarify` 是一等公民**——AI 审阅 spec,识别未决策盲点,按影响排序,**一次一个问题**,答案直接写回 spec;澄清完才允许进 plan。这正是"大需求反复对齐"的工程化形态。
- **缺陷 triage 最佳实践**(CloudBees/Ranger/ReportPortal 等):失败归因三分类 **product bug / flaky test / environment**;结构化 triage 流程 + AI 辅助分类是行业趋势;核心指标是"测试失败到缺陷关闭的反馈环时长"。
- **GitHub PR review 三态**:approve / request changes / comment——评审必须有"打回"通道,否则是审批表演。
- **ADR(Architecture Decision Records)**:分歧与决策落档,新人可追溯"当时为什么这么定"。

## 3. 设计:三个一等公民

### 3.1 对齐层 —— 评审是有来有回的协商

```
大需求导入(自由文本,多大都行)
  → [Clarify] 澄清问题清单(Q-001..n)
       每题:{问题, 为什么重要, 建议选项, 状态:待答/已答, 答案落入哪条需求}
       AI 起草(可),人逐题回答;答完可触发 AI 追问
       全部关闭 → 才允许进入 Define 起草
  → 原子需求条目(REQ-ITEM-001..n)
       {描述, 验收标准, 优先级, 状态: proposed→in-review→approved→changed, 来源=原文或某澄清答案}
  → Define 起草(人或 AI 起草)→ 提交评审
  → 评审三态(GitHub PR 式):
       approve            → 基线 vN 冻结(G1)
       request-changes    → 结构化意见(挂在具体条目上)→ 修订 → Define vN+1 → 重新评审
       每次修订产生版本链;意见与决策永久保留(可追溯"当时为什么改")
  → 变更管理:基线批准后任何条目修改 → 状态 approved→changed → 触发推进层影响分析
```

### 3.2 推进层 —— 事件驱动的缺陷与变更

```
测试失败(注入或真实)
  → [归因卡] AI 建议:product / test / infra + 理由(引用日志与断言)→ 人确认
       product → 自动创建 DEFECT(关联用例/需求/证据)→ 状态 open→fixing→fixed→verified→closed
                  → defect 阻塞对应验收门禁 → DAG 自动插入"修复任务" → 修复后重跑用例 → verified → 门禁解锁
       test    → 用例进 FLAKY/隔离清单,不算产品失败
       infra   → 基础设施修复任务,按策略重试
需求条目或契约变更
  → [影响分析] 沿追踪链(12.2)标记下游:受影响任务状态回 planned + 标 stale(注明"依赖契约 v1,现 v2")
       受影响用例标"需回归" → ready 队列自动重算 → 视图上能看到传导(谁因什么被打了回来)
```

**推进视图(新首页):"我的车道"** —— 不再是顺序点按钮,而是当前所有需要人的事项:
待我回答的澄清问题 / 待我评审的 Define / 待我归因的失败 / open 的缺陷 / 需回归的 stale 用例 / 可运行任务。处理完一项少一项。

### 3.3 AI 角色层 —— DSH 会话成为流程角色

每个 AI 参与点定义为**工作台任务**(带上下文包 + 结构化回写),由 DSH Agent 预设承接:

| 角色(DSH 预设) | 流程节点 | 输入(上下文包) | 产出(结构化回写工作台) |
|---|---|---|---|
| `fw-clarifier` | Clarify | 原始需求 + 已有问题 + 产品基线 | 澄清问题清单(逐题,带影响标注)|
| `fw-definer` | Define 起草/修订 | 需求条目 + 澄清答案 + 评审意见 | Define 草稿(条目化,进"待评审")|
| `fw-triager` | 失败归因 | 用例 + 日志 + 证据包引用 | product/test/infra 建议 + 理由(人确认)|
| `fw-impactor` | 变更影响分析 | 变更 diff + 追踪链 | 受影响任务/用例清单(人确认后执行标记)|

机制要点:
- **上下文包**:工作台把该节点需要的全部事实打包(AI 不用自己翻库)
- **结构化回写**:AI 通过新工具(`requirement_add_question`、`define_propose`、`triage_suggest`、`impact_report`)写回,产出进入**待评审态**——工具调用天然走 DSH 审批,人始终是签署方
- **降级路径**:每个 AI 节点都有"手动填"入口(模板 + 人写),AI 是增强不是依赖——没配 key 也能走完全流程(与现状兼容)

## 4. 演示剧本重做:讲一个"会失败的故事"

自动演示不再是 10 段顺顺利利,而是包含三次"真实世界事件":

1. **澄清现场**:导入大需求"做一台打印机固件"→ AI 生成 5 个澄清问题 → 演示者回答 → 需求条目化
2. **评审打回**:Define v1 提交 → 评审人 request-changes("缺纸恢复策略未定义")→ 修订 v2 → 再批准——展示版本链与意见留痕
3. **中途变更 + 缺陷**:开发进行中需求条目变更(份数 1→2)→ 影响分析把 3 个任务/2 个用例标红 stale → 重跑;集成测试故意失败 → 归因 product → DEFECT-001 创建 → 门禁变红 → 修复任务出现 → 修复 → 回归通过 → 门禁解锁 → 验收 PASS

这才证明了闭环:**系统会在该卡的地方卡住,并带你看清为什么卡、怎么解开**。

## 6. 取舍与风险

- **复杂度**:store schema 迁移是破坏性的(MVP 阶段直接重建 demo 库即可,不做兼容)
- **AI 产出质量**:所有 AI 产出都是"草稿待评审",不阻塞流程;无 key 时手动路径完整
- **不做**:多项目/多人协作、审批流引擎、通用 issue 系统——保持单机单设备 MVP 边界

## 7. 知识资产与自我进化(v2.1 增补,回应"loop 要能反哺、系统要能进化")

### 7.1 核心主张

流程的每次 loop(澄清问答、评审打回、失败归因、变更传导)都在生产知识;**沉淀不是目的,反哺才是**——知识必须自动出现在"下一个正在做这件事的人和 AI 面前",否则只是又一个没人看的库。进化 = 沉淀(自动)→ 归纳(半自动)→ 反哺(嵌入流程)→ 反馈(信号回路)。

### 7.2 四类知识资产

| 类型 | 内容 | 来源 loop | 举例 |
|---|---|---|---|
| **Fact 事实** | 领域事实、约束、参数 | 澄清答案、Define 条目、决策 | "该基线不支持 A3""引擎预热上限 8s" |
| **Pattern 模式** | 从多次 loop 归纳的检查项/启发式 | 评审意见×N、归因×N | "恢复策略是 Define 高频漏项""扫描超时类失败 40% 是模拟器时序" |
| **Case 案例** | 完整 loop 实例(可检索相似) | 缺陷全生命周期、一次变更传导 | DEFECT-001:现象→归因→根因→修复→回归 |
| **Template 模板** | 提问模板/检查单/归因框架 | 归纳产物,可继续被修订 | 证卡类需求的澄清提问模板 |

知识条目统一形态:`KNOW-{id, type, scope 标签[模块/接口/产品基线/用例类型], body, source refs(指向产生它的事件/决策/缺陷——可溯源), status[draft→proposed→approved→deprecated], usage 统计}`。**知识也是带版本与来源的一等资产**,复用证据仓的不可变理念。

### 7.3 反哺:嵌入流程的五个注入点(不是知识库页面)

| 注入点 | 反哺内容 | 机制 |
|---|---|---|
| Clarify 生成问题 | 相似需求的历史问题、已答领域事实(不重复问)、提问模板 | fw-clarifier 的上下文包自动注入 scope 匹配的 Knowledge |
| Define 起草/评审 | 评审检查单(历史 request-changes 高频漏项归纳) | 起草时作为 checklist 展示;评审时作为 lint 参考 |
| 失败归因 | 相似失败案例 + 历史归因分布 | fw-triager 上下文注入(按用例/模块/错误码签名检索) |
| 变更影响分析 | 该接口/模块的历史传导记录("过去改它平均波及 X 个任务,这 N 处常被漏") | fw-impactor 预填影响清单 |
| 测试设计 | 缺陷闭环后若"漏测"(无用例覆盖该场景)→ 自动生成补用例建议 | defect closed 且无关联用例时触发,进测试 backlog |

### 7.4 进化:三层机制

1. **被动沉淀(自动,零成本)**:v2 所有 loop 的结构化产物天然入库,必须带 source refs——**这是 P-A/P-B 的 schema 设计约束,不后补**(知识无法溯源就失去可信度)。
2. **主动归纳(半自动)**:"策展"任务——AI 从 N 条同类评审意见归纳一条检查项、从 M 个相似归因归纳一条启发式,**AI 起草 → 人批准**(与缺陷同样的"草稿→评审"工作流);fw-curator 角色承接。
3. **使用反馈(信号回路)**:记录每条知识的引用次数与结果关联(引用某检查项后评审仍漏 → 降级/修订;引用某案例后归因正确 → 权重上升)。approved 知识才进反哺注入,防止错误模式污染流程。

### 7.5 与 DSH 的结合

- 新增工具:`knowledge_search`(按 scope 检索,供 AI 会话直接问)、`knowledge_propose`(AI 归纳的草稿回写,走 DSH 审批)
- AI 角色的上下文包生成时,自动附带检索到的 top-k 知识(这就是"系统学过了"的体感来源)
- 座舱新增"知识"视图:按类型/scope 浏览、来源追溯(点开任意条目看到它诞生于哪次 loop)、待归纳提案队列

### 7.6 演示剧本再进一步

"会失败的故事"里加一段**反哺现场**:第二个缺陷出现时,fw-triager 引用历史相似案例,归因建议直接命中且附案例链接——观众看到的不是"AI 猜得准",而是"系统从上一次失败里学到了东西"。

### 7.7 分期修订(并入第 5 章)

- **P-E1 埋点(必须并入 P-A/P-B 设计,零额外工作量)**:loop 产物入库时带 source refs 与 scope 标签
- **P-E2 反哺注入(2-3 天)**:knowledge 表 + 检索工具 + 上下文注入 + 知识视图
- **P-E3 主动归纳(2-3 天)**:curator 预设 + knowledge 提案工作流 + 使用反馈统计
- 明确不做:通用知识图谱、跨产品迁移、自动无人审核的知识生效

## 8. 方案审核修订(v2.2,基于真实场景压力测试)

> 审核方法:用真实固件研发场景逐段压测第 3/7 章设计。结论:主体成立,发现 5 个实质缺口(G1-G5)、5 个补强项(G6-G10);G1/G2 影响 P-A schema,必须在开工前并入。

### 8.1 实质缺口

**G1|归因缺第四类:spec-bug(验收标准本身错了)——对齐层与推进层的断线**
真实场景:测试失败,查了半天发现不是产品错、也不是测试脚本错,是**当初验收标准定错了**(比如把 30s 超时写成 3s)。业界三分类(product/test/env)不覆盖它。这类失败的正确动作不是修代码,而是**回流为需求条目变更**,走 3.1 的变更管理 → 影响分析。它是两个一等公民之间的桥,漏掉它归因闭环是断的。
→ 修订:归因四分类 `product / test / infra / spec`;spec 归因自动生成"需求变更提案"(带失败证据引用),人确认后进变更流程。同时它是最有价值的知识("我们当初以为 X,后来发现 Y"——认知修正类 Case)。

**G2|多需求并行:schema 级缺口**
真实项目不会一次只有一个需求:复印、扫描到 U 盘、节能、驱动适配……多个需求处在不同阶段(一个在澄清、一个在开发、一个在验收)。当前设计与实现都是"单需求贯穿"(REQ-COPY-0001 一条道),"我的车道"隐含了多需求但 schema 是单数。**必须在 P-A 就按多需求建模**:需求集合(而非全局唯一)、需求间依赖(dependsOn)、车道按需求分组。开工后改 = 全部返工。
→ 修订:P-A schema 直接多需求;演示种子改为 ≥2 个需求并存(一个走完全程,一个中途插入),车道演示才有说服力。P-A 预估上调为 4-6 天。

**G3|缺陷没有严重度,验收没有偏差通道**
真实发布从不零缺陷:关键缺陷阻塞门禁,**次要缺陷走 waiver(带期限的偏差批准)发布**。总方案 12.5 本来就有 WAIVED 语义,v2 没接上。没有 waiver 通道,验收门禁是"全或无",不符合真实产品决策。
→ 修订:defect 加 severity(critical/major/minor);critical 阻塞门禁,minor 可提 waiver{范围、理由、期限},**到期自动回开**并进车道;waiver 决策入证据包。

**G4|知识冷启动:空库没有反哺可演示**
"自我进化"第一次跑时知识库是空的,反哺注入点无米下锅。最合理的种子:**总方案 v1.0 本身就是第一批知识**——12.3 打印机验收目录(Fact/Template)、11 章分层测试策略(Template)、17 章安全分级(Fact)结构化入库。
→ 修订:新增 P-E0(0.5 天):方案文档种子化注入。演示时"第一次失败学到东西、第二次命中"的故事才成立。

**G5|变更没有来源分类,"实现中发现"是最容易被漏的变更源**
当前设计变更 = "基线批准后修改",隐含都是客户/上级发起。真实研发大量变更是**实现中发现的认知更新**(做到一半发现两个模块对某行为的理解不一致)和**测试反馈**(G1 的 spec-bug)。这三类的处理路径不同(客户变更要评估影响再谈,认知更新往往要连带改契约)。
→ 修订:变更记录 source:`customer / implementation-finding / test-finding`;implementation-finding 类变更强制关联"当时的错误认知"——天然是知识资产的 Case 来源。

### 8.2 补强项

- **G6 知识腐化**:approved 知识加复审周期(默认 90 天,Fact 类 180 天),到期进车道"待复审";使用反馈已有降级机制,加时间是双保险。
- **G7 车道排序**:多事项并存时按"是否在关键路径 + 等待时长"排序(复用 8.6 调度优先级思想),不靠人肉翻。
- **G8 演示与真实数据隔离**:演示注入的失败/缺陷标记 `demo:true`,**不进**知识使用统计与归因分布——否则演示污染进化信号。
- **G9 需求间依赖**:REQ 条目加 dependsOn(P-A 顺手);真实需求常互相依赖(扫描到 U 盘依赖 USB 栈需求)。
- **G10 撤销与修正**:误批准/误归因需要修正通道——证据不可变,但状态可修正;修正本身留决策记录(谁、何时、为何改)。轻量:Decision 表已有雏形,补 correction 类型。

### 8.3 修订后分期(替换第 5 章)

| 期 | 内容 | 预估 |
